# Migrating from 0.9 to 1.0

Orrery 1.0.0 is a deliberate, one-time break against 0.9.x. It removes the hidden
binary-compatibility bridges that piled up before 1.0, drops one duplicate entry point and
turns the growth-prone data classes into plain classes, so that 1.x can grow without
breaking you again. After 1.0 the rules in [API-STABILITY.md](../API-STABILITY.md) apply:
no break inside a major version.

Every change on this page comes from the API audit ledger,
[`docs/api-audit-1.0.md`](../api-audit-1.0.md). The row IDs (`B-001`, `S-001`, `D-004`, …)
are the ledger's, so you can look up the details of any row there. The
[CHANGELOG](../../CHANGELOG.md) lists the same changes under `BREAKING`.

**In short:**

1. Update every `me.kozakov.orrery` artifact to the same 1.0 version.
2. Rename `CalendarDefaults.DaysOfWeekHeader` to `WeekHeader` ([X-001](#x-001-calendardefaultsdaysofweekheader-is-removed)).
3. Replace destructuring of the converted classes with property access ([data classes](#data-classes-that-became-plain-classes)).
4. Recompile. Everything else is source compatible.
5. If you publish a library that depends on Orrery, publish a build compiled against 1.0.

## Who is affected

**Apps and libraries compiled against 0.9.x or earlier.** Most of the removed declarations
were invisible to source code, so your sources still compile against 1.0, but the bytecode
or klib you built against 0.9.x links signatures that 1.0 no longer has. Mixing the two
fails with `NoSuchMethodError` at run time on the JVM and Android the first time the old
signature is called (on iOS and Wasm, with a Kotlin linkage error).

- **Your app:** recompile it against 1.0 and fix the two source breaks below (X-001 and
  destructuring). That is the whole migration for most apps.
- **Your library:** if your library depends on Orrery, recompile it against 1.0, fix the
  same source breaks and publish a new release that requires Orrery 1.0. A build of your
  library compiled against 0.9.x is not safe to use with Orrery 1.0.
- **The transitive case:** an app on Orrery 1.0 that uses a third-party library built
  against Orrery 0.9.x can crash with `NoSuchMethodError` inside that library, even though
  the app itself compiles and its own code is fine. Gradle resolves one Orrery version
  for the whole app (the newest one), so the library runs against 1.0 without being
  rebuilt for it. To fix it, use a release of the library built against Orrery 1.0, or ask
  its authors for one; until then, stay on Orrery 0.9.x. To see which of your dependencies
  pull in Orrery, run
  `./gradlew :app:dependencyInsight --dependency me.kozakov.orrery --configuration releaseRuntimeClasspath`
  (use the runtime classpath configuration of your variant or target).

You are **not** affected by the binary break if you compile everything that touches
Orrery yourself, from source, against 1.0.

### B-046: compiler-generated `ComposableSingletons` getters

**Not a bridge. No source change.** The Compose compiler generated these public getters
for the default slot lambdas of B-014 to B-019: eight in `ComposableSingletons$CalendarsKt`
(from B-014 to B-018) and one in `ComposableSingletons$CollapsibleCalendarScaffoldKt` (from
B-019). They went away with the bridges. Your code never calls them by name; recompile,
as for the bridges.

## X-001: `CalendarDefaults.DaysOfWeekHeader` is removed

**Source break.** `CalendarDefaults.DaysOfWeekHeader` was an alias of
`CalendarDefaults.WeekHeader` (added in 0.9.0). 1.0 removes it rather than carrying a
duplicate entry point through all of 1.x. `WeekHeader` takes the same parameters, so
rename the call:

```kotlin
// 0.9.x
weekHeader = { daysOfWeek ->
    CalendarDefaults.DaysOfWeekHeader(daysOfWeek, weekendContentColor = Color.Red)
}

// 1.0
weekHeader = { daysOfWeek ->
    CalendarDefaults.WeekHeader(daysOfWeek, weekendContentColor = Color.Red)
}
```

## Data classes that became plain classes

The configuration, state and result types below were `data class`es. A data class cannot
gain a property without changing its constructor, `copy` and `componentN` functions, which
is a break every time. In 1.0 they are plain classes with defaults on the constructor and
a hand-written `copy`, `equals`, `hashCode` and `toString`.

What this means for your code:

- **Destructuring stops compiling** (source break): there are no `componentN` functions any
  more. Read the properties by name.
- **`copy(...)` still works** with the same parameter names and defaults.
- **Constructors keep their parameters and defaults.** Use named arguments: they are the
  form that stays valid when 1.x adds a parameter.
- **`equals`, `hashCode` and `toString`** give the same results as before, so maps, sets,
  `remember` keys and tests behave the same.
- **Binary break:** the generated `componentN` functions are gone, so code compiled against
  0.9.x that destructured these types needs a recompile.

```kotlin
// 0.9.x
val (id, title) = event                    // CalendarEvent
val (date, ruleId) = holiday               // PublicHoliday
calendarState.visibleMonthChanges().collect { (month, source) -> println("$month $source") }

// 1.0
val id = event.id
val title = event.title
val date = holiday.date
val ruleId = holiday.ruleId
calendarState.visibleMonthChanges().collect { change -> println("${change.month} ${change.source}") }
```

`copy` and construction are unchanged; prefer named arguments:

```kotlin
val standup: CalendarEvent<Nothing> =
    CalendarEvent(
        id = "standup",
        title = "Standup",
        span = EventSpan.AllDay(LocalDate(2026, 11, 17)),
    )
val moved = standup.copy(title = "Standup (moved)") // same as in 0.9.x
```

## New: experimental `orrery-widget`

1.0 adds `me.kozakov.orrery:orrery-widget`, headless month, week and agenda-strip
snapshots for app widgets and share images ([guide](../guide/widgets-and-snapshots.md)).
It is a new artifact, so nothing breaks, but:

- **No compatibility promise until it graduates (planned for 1.1).** Every public
  declaration is `@ExperimentalOrreryApi` and needs an opt-in. It can change in any 1.0.x release, and
  the ABI gate does not check it. The plan is to remove the marker in 1.1 after an API
  review.
- **Use `orrery-widget` and `orrery-compose` at the same version.** The widget module calls
  internal drawing code of `orrery-compose`; its Gradle metadata pins the exact version, so
  a mismatch fails dependency resolution. Keep every `orrery-*` artifact on one version
  anyway.

## Release candidates and the compatibility gate

1.0.0 ships as `1.0.0-rc.1` on Maven Central first, followed by about a week of soak
before `1.0.0`.

- **From `1.0.0-rc.1` on, the gate protects compatibility.** CI compares the public ABI of
  every change with the last release (the RC, later `1.0.0`) and fails on any removal or
  signature change; the temporary allow-list that let the 1.0 breaks above through is
  emptied by the first change after the RC is tagged. See [API-STABILITY.md](../API-STABILITY.md#how-the-abi-gate-works).
- **A break found during the soak means a new RC.** If testing `rc.1` shows that another
  break is needed, it needs Andrii's approval on #89, ships as `1.0.0-rc.2` and starts a
  new soak. `1.0.0` itself contains no break against the last RC.

Trying the RC is the best way to find problems in your app or library early. Please report
them: open an issue and mention [#89](https://github.com/koza4e4ok/Orrery/issues/89).

## Built and tested with

1.0 is built with the same Kotlin, Compose Multiplatform and kotlinx-datetime versions as
0.7.0 to 0.9.2. On Android it moves to Compose 1.13 (BOM 2026.11.01), which needs
`compileSdk 37.1`: an Android app or library that depends on `orrery-compose` or
`orrery-widget` must compile against API 37.1 or later, or its `checkAarMetadata` task
fails. With AGP 9, set `compileSdk { version = release(37) { minorApiLevel = 1 } }`.
The versions (`gradle/libs.versions.toml`):

| --- | --- | --- | --- | --- | --- |
| 2.4.21 | 1.12.2 | 1.9.0 | 2026.11.01 | 0.8.0 | 37.1 / 23 |

These are the versions Orrery is built and tested with, not a promised range: see
[API-STABILITY.md](../API-STABILITY.md#platform-and-toolchain).
